# Нагрузочный smoke MTProto (M13-T5)

    make bench-mtproto                                  # N=5000
    make bench-mtproto BENCH_MTPROTO_ARGS="-n 1000 -duration 15s -cpuprofile cpu.prof -memprofile mem.prof"

Стенд целиком в одном процессе на 127.0.0.1: фейковый Telegram, 2 dial-агента
(каждый со своим fake-DC в режиме эхо, `probe.NewFakeDCEcho`), сервер с MTProto
на shared-листенере, секрет засеян в SQLite до старта.

Фазы: (1) базовый p95 getMe (vegeta, 200 rps); (2) открытие N соединений
`probe.Dial` + эхо-пакет; (3) `-bulk` соединений гонят эхо-пакеты конвейером,
параллельно getMe — сравнивается p95; (4) закрытие всех, ожидание до 90 с,
сравнение горутин и fd с состоянием «до».

Цели (код возврата 1, если не достигнуты): N соединений; >= 200 Мбит/с
(сумма обоих направлений); p95 getMe под нагрузкой < 2x базового; нет роста
горутин/fd.

Замечания:
- RSS/fd/горутины — всего процесса (сервер + агенты + DC + клиенты): верхняя
  оценка. fd на соединение ~4. Лимит fd поднимается через setrlimit; если
  потолок ОС ниже `4N+2000`, N снижается с предупреждением (macOS:
  `sysctl kern.maxfilesperproc`, `ulimit -n`).
- Параллелизм dial ограничен 50: backlog listen на macOS 128
  (`kern.ipc.somaxconn`), при большем числе одновременных SYN часть
  соединений получает RST.
- На macOS RSS занижается сжатием памяти; ориентируйтесь на heap.
- p95 getMe в абсолютных значениях — единицы мс; отношение к базе (< 1 мс)
  шумит, прогоняйте несколько раз. Для сопоставимых цифр запускайте на
  Linux-хосте.

## Память на соединение (оптимизация h2-буферов)

Причина 71% heap: Go держит на каждый исходящий h2-поток scratch-буфер
`min(SETTINGS_MAX_FRAME_SIZE пира, 512 КиБ)` всё время жизни потока, а
`streamMaxFrameSize` был 1 МиБ. Сделано: `transport.StreamMaxFrameSize = 16 КиБ`
(dial/reverse на сервере, `http.Server.HTTP2` листенера dial-агента,
`http2.Server` MTProto-коннектора reverse); релей агента и `pump` сервера держат
в простое 1 КиБ, 32 КиБ берут из пула только пока идёт поток; `watch` релея
без отдельной горутины (таймеры + `context.AfterFunc`).

Замер на macOS arm64, `-duration 10s` (heap — после открытия N соединений):

| N | | heap | RSS | горутин | heap/соед. | горутин/соед. | эхо, Мбит/с |
|---|---|---|---|---|---|---|---|
| 1000 | до | 689 МБ | 398 МБ | 9073 | 689 КБ | 9.0 | 613 |
| 1000 | после | 130 МБ | 224 МБ | 8070 | 130 КБ | 8.0 | 617 |
| 5000 | до | 3440 МБ | 1295 МБ | 45118 | 688 КБ | 9.0 | 611 |
| 5000 | после | 608 МБ | 952 МБ | 40118 | 122 КБ | 8.0 | 618 |

Размер фрейма (N=1000, эхо в Мбит/с): 16 КиБ — 591/594, 32 КиБ — 595/576,
64 КиБ — 612/598 (в пределах шума), heap 130/147/175 МБ. Выбрано 16 КиБ.

Известно: на N=5000 p95 getMe под нагрузкой 2.3–2.8x базового как до, так и
после (клиенты, сервер и агенты делят CPU одной машины) — цель `< 2x` на
macOS не показательна, смотрите на Linux-хосте.
